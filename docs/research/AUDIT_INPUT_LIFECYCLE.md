# Audit: input device and grab lifecycle

Scope: `crates/infynitae-backend-drm/src/lib.rs`, `crates/infynitae-core/src/{lib.rs,entry.rs,input/focus.rs}`, `crates/infynitae-wayland/src/{lock.rs,layers.rs,outputs.rs,pointer.rs,handlers.rs,x11_keys.rs,virtual_input.rs}`, and `vendor/smithay-0.7.0/src/{input,wayland/seat,desktop/wayland/popup}`.

## Bugs

### 1. `Super` (`Mod4`) stays depressed on leaving client (`Super+Tab`, `Super+A`, fullscreen switches) and `x11_keys` desyncs on lock or satellite restart

On the Wayland wire (`vendor/smithay-0.7.0/src/input/keyboard/mod.rs:57-69, 1333-1367`, `vendor/smithay-0.7.0/src/wayland/seat/keyboard.rs:167-235`), `WlSurface::leave` sends `wl_keyboard.leave` without first sending a `wl_keyboard.modifiers` event clearing `depressed` modifiers or releasing compositor-consumed modifier keys on the outgoing surface. When a client holds focus, receives `KEY_LEFTMETA` (`125`, `Mod4` / `0x40`) down (`crates/infynitae-core/src/entry.rs:682-699`), and then loses keyboard focus because `Super+Tab` switches focus (`crates/infynitae-wayland/src/outputs.rs:75-130`) or `Super+A` launches an overlay (`crates/infynitae-wayland/src/outputs.rs:329-375`), the leaving client sees:
`wl_keyboard.key 125 pressed` -> `wl_keyboard.modifiers dep=0x40 lat=0x0 lock=0x0` -> `wl_keyboard.leave`, with no `dep=0x0` reset and no `wl_keyboard.key 125 released`.
Proved by `super_tab_leaves_super_depressed_on_leaving_client_wire` in `crates/infynitae-backend-headless/tests/audit_input_lifecycle.rs`.

For X11 apps behind `xwayland-satellite` (`crates/infynitae-wayland/src/x11_keys.rs:51-73, 88-132`):
- When another surface is focused and unlocked, `Effect::KeyboardForward` (`crates/infynitae-wayland/src/outputs.rs:180-188`) calls `forward_key_to_x11`, which forwards `125` (`Super`) to the satellite client's keyboards without focus and inserts `125` into `x11_keys.pressed`.
- If the session locks via `start_locked()`/`lock_now()` (`crates/infynitae-wayland/src/lock.rs:127-149, 172-204`), `x11_keys.pressed` is never cleared, and subsequent key releases hit `lock_key(...)` (`kb.input_intercept` + `return true` at `lock.rs:175-180`), bypassing `core_key` and `forward_key_to_x11`. Proved by `x11_keys::tests::lock_swallows_release_of_x11_forwarded_key`.
- When locking via `SessionLockHandler::lock` (`crates/infynitae-wayland/src/lock.rs:475`), `self.x11_keys.pressed.clear()` drops tracked keys without sending `KeyState::Released` to the X11 client's keyboards.
- If `xwayland-satellite` restarts and a new connection calls `note_x11_client` (`crates/infynitae-wayland/src/x11_keys.rs:88-92`), `self.x11_keys.pressed` is preserved across the client replacement so the next release sends an unmatched `KeyState::Released` to the new client. Proved by `x11_keys::tests::note_x11_client_clears_pressed_keys_on_satellite_replacement`.

`xwayland-satellite` and XWayland internal modifier state updates upon receiving `wl_keyboard.leave` with `depressed=0x40` or unfocused `wl_keyboard.key` events without `wl_keyboard.modifiers` were **not checked**.

**Fix:** Send a cleared `wl_keyboard.modifiers` (`depressed=0`) or release compositor-held modifiers cleanly before leaving the surface when focus shifts via compositor shortcuts; send `KeyState::Released` for every key in `x11_keys.pressed` when locking (`start_locked` and `SessionLockHandler::lock`), and clear `x11_keys.pressed` when `note_x11_client` replaces `x11_keys.client`.

### 2. `start_locked`/`lock_now` and `Effect::LayerKeyboardFocus` skip popup grab teardown

Two paths assign keyboard focus while a popup grab (`PopupKeyboardGrab`) can still be active on the seat:
1. Calling `start_locked()` / `lock_now()` (`crates/infynitae-wayland/src/lock.rs:127-149`) sets `l.locked = true` immediately so when the lock client connects and commits, `SessionLockHandler::lock` (`crates/infynitae-wayland/src/lock.rs:453-484`) sees `if l.locked` and returns early, skipping `dismiss_popup_grab()`. Later, `lock_key` (`crates/infynitae-wayland/src/lock.rs:186-194`) calls `kb.set_focus(..., lock_surface, ...)` *before* `keyboard_unset_grab()`. `PopupKeyboardGrab::set_focus` (`vendor/smithay-0.7.0/src/desktop/wayland/popup/grab.rs:456-476`, `vendor/smithay-0.7.0/src/input/keyboard/mod.rs:891-898`) rejects changing focus to the unrelated lock surface, so the first keystroke press after locking goes to the app's popup instead of the lock surface, leaving the press unmatched when `keyboard_unset_grab()` clears the grab right after. Proved by `lock_now_with_popup_grab_routes_first_key_to_popup_and_leaves_held_key`.
2. Applying `Effect::LayerKeyboardFocus` (`crates/infynitae-wayland/src/layers.rs:155-164`, `crates/infynitae-wayland/src/outputs.rs:75-130`) when an `Exclusive` layer surface maps/commits (unlike `Effect::KeyboardFocus` in `entry.rs:359-365, 2666-2672`) never calls `dismiss_popup_grab()` or `keyboard_unset_grab()`, so `PopupKeyboardGrab::set_focus` refuses focus transfer to the exclusive layer and the open popup keeps receiving keys. Proved by `layer_keyboard_focus_does_not_dismiss_popup_grab`.

**Fix:** Call `dismiss_popup_grab()` and `keyboard_unset_grab()` before `kb.set_focus(...)` in both `lock_key` and `Effect::LayerKeyboardFocus`, and run popup/forwarded-key cleanup on `start_locked` without letting `if l.locked` skip it.

### 3. `ClickGrab` is dropped mid-press (`refuse_client_drags`, popup grab end, surface destroy) and delivers an unmatched `Released` to another client

`Core::route_pointer` (`crates/infynitae-core/src/lib.rs:2231-2276`) routes hover under the pointer without maintaining pointer `KeepFocus` across client button holds; Smithay's `ClickGrab` provides implicit pointer grab behavior (`vendor/smithay-0.7.0/src/input/pointer/grab.rs:233-250, 344-383`, `vendor/smithay-0.7.0/src/input/pointer/mod.rs:887-900`). Core still records `Owner::Client` for the held button in `ownership`, so whenever Smithay loses `ClickGrab` mid-press and returns to `DefaultGrab`, subsequent pointer motion switches `wl_pointer` focus to another surface B and releasing the button delivers `wl_pointer.button Released` to B with no preceding `Pressed`:
- `ClientDndGrabHandler::start_drag` -> `refuse_client_drags` (`crates/infynitae-wayland/src/handlers.rs:1033-1041`, `crates/infynitae-wayland/src/pointer.rs:488-507`) replaces `DnDGrab` with `PanDismissedPopupGrab` (`crates/infynitae-wayland/src/pointer.rs:150-160`), whose next motion calls `unset_grab` back to `DefaultGrab`. Proved by `refuse_client_drags_drops_click_grab_and_delivers_unmatched_release_to_second_client`.
- Pressing a button while `PopupPointerGrab` is active (`crates/infynitae-wayland/src/handlers.rs:866-895`, `vendor/smithay-0.7.0/src/desktop/wayland/popup/grab.rs:581-611`) never establishes a `ClickGrab`; when the popup grab ends mid-press (`reconcile_popup_chain` at `crates/infynitae-wayland/src/handlers.rs:147-159` or `Effect::DismissPopupGrab` at `crates/infynitae-wayland/src/outputs.rs:113-151`), Smithay falls back to `DefaultGrab`. Proved by `popup_pointer_grab_ended_mid_press_delivers_unmatched_release_to_second_client`.
- Destroying the grabbed surface mid-press makes `ClickGrab` observe `!focus.alive()` (`grab.rs:357-365`) and drop back to `DefaultGrab`. Proved by `click_grab_lost_on_surface_destroy_delivers_unmatched_release_to_second_client`.

**Fix:** Track the client surface that received each pressed pointer button (in Core or `WaylandState`) and drop `Released` events whenever the current pointer target does not match the surface that got `Pressed`.

### 4. `CameraPan` skips layer popup dismissal when no window is focused, and `DismissPopupGrab` steals keyboard focus from `Exclusive` layers

In `Core` button press handling (`crates/infynitae-core/src/entry.rs:2598-2642`), starting `CameraPan` only pushes `Effect::DismissPopupGrab` when `self.focus.target().is_some()`.
- If no window is focused (`focus.target() == None`) while a layer surface owns an open `xdg_popup` grab, starting a `CameraPan` never dismisses that popup. Proved by `camera_pan_with_layer_popup_and_no_window_focus_does_not_dismiss_popup_grab`.
- Conversely, if a window is focused under an `Exclusive` keyboard layer surface (`crates/infynitae-core/src/input/focus.rs:138-167, 260-281`), `CameraPan` does emit `Effect::DismissPopupGrab`, and `outputs.rs` (`crates/infynitae-wayland/src/outputs.rs:131-157`) unconditionally calls `kb.set_focus(..., window_surface, ...)` after ungrabbing, stealing keyboard focus away from the `Exclusive` layer back to the underlying window. Proved by `dismiss_popup_grab_on_camera_pan_steals_keyboard_from_exclusive_layer`.

**Fix:** Emit `Effect::DismissPopupGrab` unconditionally on `CameraPan`, and in `outputs.rs` only re-apply window keyboard focus if no `Exclusive` layer surface currently holds keyboard focus.

### 5. `ClickGrab` stays active when the grabbed surface unmaps mid-press

Smithay's `ClickGrab` (`vendor/smithay-0.7.0/src/input/pointer/grab.rs:357-365`, `vendor/smithay-0.7.0/src/input/pointer/mod.rs:889-890`) checks `focus.alive()` rather than surface mappedness (`crates/infynitae-core/src/lib.rs:2231-2276`). When client A receives `BTN_LEFT` pressed (`ClickGrab`) and unmaps (`attach(None)` + `commit`) before releasing the button, moving the pointer onto visible client B continues sending `motion` events to unmapped A (`A.ptr` sees motion; `B.ptr` sees no `enter`). Proved by `click_grab_kept_while_client_surface_unmapped`.

**Fix:** Check whether an active `ClickGrab` target surface is still mapped on commit/unmap (or before `ClickGrab` forwarding), and unset the grab back to `DefaultGrab` on unmap.

### 6. `disable_touch` and `SessionLockHandler::lock` cancel Smithay `wl_touch` without sending `PhysicalEvent::TouchCancel` to Core

`WaylandState::disable_touch` (`crates/infynitae-wayland/src/pointer.rs:658-684`, called by `backend-drm` on `DeviceRemoved` at `crates/infynitae-backend-drm/src/lib.rs:3857-3864`) and `SessionLockHandler::lock` (`crates/infynitae-wayland/src/lock.rs:468`) cancel Smithay's `wl_touch` handle (`cancel_touches`), but neither injects `PhysicalEvent::TouchCancel` into Core (`crates/infynitae-core/src/entry.rs:270-276, 312-330`). In `backend-drm` (`crates/infynitae-backend-drm/src/lib.rs:3674-3681`), `core_touch(data, PhysicalEvent::TouchCancel)` only runs when a physical touch event arrives while locked. If a touchscreen disconnects during an active canvas touch, or the screen locks and unlocks without any touch event arriving while locked, the old slot remains active in `Core::touches`, causing a subsequent single-finger tap on a window to be absorbed as an extra finger of the stale canvas touch. Proved by `disable_touch_leaves_core_touch_state_active` and `session_lock_leaves_core_touch_state_active_across_unlock`.

**Fix:** Submit `PhysicalEvent::TouchCancel` to Core inside `disable_touch` and on session lock so `Core::touches` always clears in sync with `wl_touch`.

### 7. `backend-drm`: `buttons_down` lacks per-device refcounting, and unlock synthesizes false releases for `VirtualPointer`/`VirtualKeyboard`

- `handle_input` (`crates/infynitae-backend-drm/src/lib.rs:3626-3632`) maintains `data.buttons_down` as a flat `Vec<u32>` (`retain` then `push` if pressed), whereas `held_by_device` (`crates/infynitae-backend-drm/src/lib.rs:3871-3910`) is per-device (`sysname`). If mouse 1 and mouse 2 both hold button `B`, releasing mouse 1 removes `B` from `data.buttons_down` while mouse 2 still holds it in `held_by_device`; a subsequent lock + unlock (`crates/infynitae-backend-drm/src/lib.rs:1915-1935`) sees `!data.buttons_down.contains(&B)` and injects `PointerButton { button: B, pressed: false }` into Core while mouse 2 still holds `B`.
- `apply_virtual_input` (`crates/infynitae-backend-drm/src/lib.rs:3315-3338`, `crates/infynitae-wayland/src/virtual_input.rs:103-122, 246-274, 412-425`) injects `VirtualInput::Button` into Core without adding it to `data.buttons_down`, and `VirtualInput::Key` without adding it to `SessionLock`'s `phys_down` (`crates/infynitae-wayland/src/lock.rs:280-291`). Unlocking therefore synthesizes releases (`1911-1936`) for buttons/keys still held by active virtual input clients. Additionally, while locked, `VirtualKeyboard::keyboard_key` (`virtual_input.rs:118-120`) still queues releases of previously held virtual keys straight to `core_key` (`backend-drm/src/lib.rs:3324-3326`), bypassing `lock_key`.

Checked in code; not run against `backend-drm` or a virtual-input harness.

**Fix:** Compute physically held buttons from `held_by_device` plus `VirtualPointer` held state rather than an un-refcounted `buttons_down` vector, and include active `VirtualKeyboard` held keys in unlock held-key reconciliation (`phys_down`) while routing virtual releases through lock-aware key handling.

### 8. VT switch (`SwitchVt`) and `PauseSession` (`libinput.suspend()`) leave held modifiers, keys, buttons, and touches active across pause

Pressing `Ctrl+Alt+Fn` in `handle_input` (`crates/infynitae-backend-drm/src/lib.rs:3703-3709`) triggers `data.seat.change_vt(vt)` and records only `Fn` in `data.taken`, while `Ctrl`, `Alt`, and any other pressed keys/buttons/touches remain held in Core and in focused clients. When logind notifies `SeatEvent::PauseSession` (`crates/infynitae-backend-drm/src/lib.rs:1445-1459`), `backend-drm` calls `data.libinput.suspend()` without releasing held keys, buttons, or touches in `held_by_device`, `buttons_down`, Core, or Smithay seats (`libinput_suspend`/`libinput_resume` C internals were **not checked**; cannot test DRM/seatd VT switches on this live machine). Any input released while switched away (if libinput suspends/recreates devices without delivering releases on resume) leaves keys (`Ctrl`/`Alt`), buttons, or touches stuck on return.

**Fix:** On `PauseSession` (or right after `change_vt`), release held physical keys, buttons, and active touches across `held_by_device`, `buttons_down`, Core, and seats, reconciling with verified `libinput_suspend`/`resume` device semantics.

## Improvements

### 1. `Core::client_drag` ignores `serial` and exact initiator button, and does not dismiss popup grabs

`Handlers` (`crates/infynitae-wayland/src/handlers.rs:767-791`) passes `_serial` unused into `Core::client_drag` (`crates/infynitae-core/src/entry.rs:1524-1587`), which picks `.find(|(_, o)| *o == Owner::Client)` from `ownership.pressed()` regardless of which button press carried the client's serial and without dismissing any active popup grab. Checked in code.

**Fix:** Pass the triggering press serial/button identity into `client_drag` and emit popup grab dismissal before starting the move or resize interaction. Size: S.

### 2. `SeatHandler::focus_changed` is skipped when keyboard focus clears to `None`

`KeyboardHandle::set_focus` (`vendor/smithay-0.7.0/src/input/keyboard/mod.rs:1361-1367`) calls `data.focus_changed(self.seat, Some(&focus))` on focus set, but in the `None` branch only calls `old_focus.leave(...)` without calling `data.focus_changed(self.seat, None)`. In `crates/infynitae-wayland/src/handlers.rs:939-945`, `data_device` focus, primary selection focus, and `update_shortcuts_inhibit` are updated inside `focus_changed`, so clearing keyboard focus to `None` leaves those states pointing at the previous client. Checked in code.

**Fix:** Call `focus_changed(seat, None)` when unsetting keyboard focus to `None` (or explicitly clear data-device/primary focus and shortcuts inhibit in `outputs.rs` when focus becomes `None`). Size: S.

### 3. `x11_keys::forward_key_to_x11` sends `wl_keyboard.key` without `wl_keyboard.modifiers`, and unfocused `pressed` entries persist across focus gain to X11

`forward_key_to_x11` (`crates/infynitae-wayland/src/x11_keys.rs:96-132`) forwards `keyboard.key(...)` to `xwayland-satellite` without updating `wl_keyboard.modifiers`. Also, if a key is pressed while a Wayland surface has focus (inserted into `x11_keys.pressed`) and released after focus moves onto an X11 window, line `115` executes `self.x11_keys.pressed.remove(&key) && !focus_is_x11` (removing the key from `pressed`, skipping duplicate `forward_key_to_x11` release — which assumes `xwayland-satellite` merges unfocused forwarded presses cleanly with focused surface events; `xwayland-satellite` internal handling not checked). Checked in code.

**Fix:** Send updated `wl_keyboard.modifiers` to the satellite connection when forwarded modifier keys change while unfocused, and reconcile `x11_keys.pressed` whenever focus transitions to or from an X11 client. Size: S.

### 4. `lock_key` sets keyboard focus before `keyboard_unset_grab()` for all grab types

In `crates/infynitae-wayland/src/lock.rs:186-194`, `lock_key` invokes `kb.set_focus(..., lock_surface, ...)` before `keyboard_unset_grab()`. Even outside `PopupKeyboardGrab` (covered under Bug 2), any custom `KeyboardGrab` active on the seat can intercept or block focus transfer for one key event before being unset. Checked in code.

**Fix:** Call `keyboard_unset_grab()` before `kb.set_focus(...)` inside `lock_key`. Size: S.

### 5. `DeviceRemoved` skips `disable_touch()` when another touchscreen remains attached

In `crates/infynitae-backend-drm/src/lib.rs:3857-3864`, `DeviceRemoved` only calls `disable_touch()` when no remaining device in `data.input_devices` has `DeviceCapability::Touch`. Disconnecting one touchscreen while a second touchscreen is attached leaves any active slot from the removed device uncancelled in Core. Checked in code.

**Fix:** Track active touch slots per device (like `held_by_device`) or inject `TouchCancel` on every touch-capable `DeviceRemoved`. Size: S.
