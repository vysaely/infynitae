# G-OB24 — decision requirements and recommendation (2026-10-16)

Status: **PROPOSAL for the owner. Nothing is adopted. OB-24 stays OPEN; INC-10 must not start
until G-OB24 and the zoom-domain amendment (A1, `ZOOM_CONTRACT.md`) are decided.**

Evidence: `README.md` (INC-9 harness on `experimental/inc-9-ob24-evidence`): under the sealed
rule `R_O = floor(v_O/120)·120`, widths and gaps change by ±1 px 3–11 times per pan at an
effective scale `k ∉ n/120` (none at `k ∈ n/120`); with `R` held fixed, none; render/hit
agreement exact either way.

## 1. What has to be decided

| # | Question | Recommendation |
|---|---|---|
| Q1 | Who owns the lattice reference `R`? | **The output's projection state, not the camera.** `R` depends on `v_O`, `view_O` and `scale_O`, all output facts. Core holds a per-output `ProjectionAnchor { r: (i64, i64), k: f64, view: (u32, u32) }` beside the output model; the camera keeps `(centre, zoom)` only. |
| Q2 | Its lifetime? | Fixed when the output's view is (re)defined: output connected, camera bound, `k_O` changed (camera zoom, output scale), `view_O` changed (mode, transform). Kept across pans. Dropped with the output. |
| Q3 | When is it re-anchored? | Only at those events, and additionally when `|v_O − R|` would exceed the exact range (`2³⁷` px, F-VIEW-1): a pan across the whole Canvas re-anchors once, a defined and rare event. Never per frame of a pan. |
| Q4 | Per-output behaviour? | Each output re-anchors independently; a window spanning two outputs is rounded per output (as today). Two outputs with different scales have different `k`, hence different `R` lifetimes. |
| Q5 | Persistence? | **Optional, separate from cameras:** a versioned `projection` table keyed by `OutputKey` (`R`, `k`, `view`) beside the camera table. Restored only if `k` and `view` still match on connect; otherwise re-derived. |
| Q6 | Backward compatibility? | Files without the table are valid: `R` is derived on connect (a one-time ±1 px shift of some widths relative to the previous session). Under A1, a camera table with a zoom outside the domain is rejected whole (M20 all-or-nothing); the owner may prefer to drop only that entry — a separate decision, listed in §3. |
| Q7 | Zoom steps (discrete zoom, INC-10)? | Each step changes `k`, so each step re-anchors; widths re-round once per step. That is the existing behaviour of a zoom and is not jitter. |
| Q8 | **Animated zoom** (a zoom that changes `k` every frame)? | Not solved by any `R`: every frame re-rounds every edge, so relative ±1 px jitter appears. Options below; **recommend Z2** for `k ≥ 1/120` and Z1's acceptance below it. |
| Q9 | Continuity? | The camera centre stays continuous (`c_eff` within half a physical px, F-LATTICE-1). Re-anchoring moves no edge by more than ±1 px and only at the events of Q2/Q3. |

### Animated zoom (Q8)

| Option | What | Cost |
|---|---|---|
| Z1 accept | re-anchor every frame; ±1 px relative jitter during the animation only | visible on thin gaps; needs a T3 visual verdict |
| **Z2 lattice steps** | animated zoom passes only through effective scales `k ∈ n/120` (exact widths, no jitter at all, the INC-9 controls); the resting zoom is one of them | steps are 1/120 in `k`: < 1 % per step at `k ≥ 1`, coarser when zoomed out; below `k = 1/120` no lattice exists, so Z1 applies there |
| Z3 unsnapped during motion | render at fractional positions while `k` animates, snap at rest | needs sub-pixel element placement in the renderer (F-RENDER-1 amendment; Smithay places elements at integer physical points), and hit testing on unsnapped geometry |

## 2. Proposed amendment text (A2, for approval)

F-LATTICE-1, `R_O`: "is the output's projection anchor: set to `floor(v_O / 120)·120` when the
output's view is (re)defined — connect, camera bound, `k_O` changed, `view_O` changed — and when
`|v_O − R_O|` would exceed 2³⁷ px; kept otherwise. It belongs to the output's projection state,
not to the camera, and may be persisted per `OutputKey`, restored only when `k_O` and `view_O`
match." INV-RENDER-1's extracted text follows. Animated zoom: "an animated zoom passes only
through `k ∈ n/120` while `k ≥ 1/120`" (Z2), or the owner's choice of Z1/Z3.

## 3. Decisions the owner must make

1. A1 (representable domain) — adopt, and choose whether an out-of-domain persisted zoom rejects
   the camera table (current M20 rule) or only its entry.
2. G-OB24: pinned anchor per output (recommended) / gesture-pinned / conservative fallback.
3. Animated zoom: Z2 (recommended) / Z1 / Z3.
4. Persist the projection anchor (Q5) or always re-derive it.

## 4. Not covered by evidence yet

Multi-output pans with different scales (the algebra is per output; no harness run), the visual
T3/T4 verdict on Z1, the cost of Z2's stepping for the zoom gesture feel (INC-10), a GPU renderer.
